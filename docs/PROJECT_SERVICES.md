# A project's modules as services

**Status: designed, not built.** Nothing in this file runs today. What runs today is the
platform's own fleet — `services.yaml`, `tools/gen_fleet.py`, `SERVICE_CONTRACT.md`,
`templates/service/`, `conductor/app/fleet.py`, the `/svc` gateway and the Atlas — and this
note audits how much of that is already shaped like a *project's* fleet, what is repo-rooted
and would have to move, what the manager would have to learn, and the four things nobody has
solved. The rule being generalised is the owner's, unchanged: **a module means a
microservice.** It applied to the platform first because the platform was the codebase we
could afford to break.

## The shape

A user's project decomposes the way this one did: a module of their software is a directory
nobody has to read — one process, one port, one database it alone opens, one committed
contract, green under process-compose on first boot.

It is **scaffolded from `templates/service/`** into `services/<name>/` **inside the
project's own repository** — `app.py`, the vendored `helpers.py`, `openapi.json`, `tests/`,
an optional `ui/panel.html`, a `SERVICE.md` the agent fills in — and is ordinary source code
the agent commits on its branch, which is the point: a module is a repository artifact, not
a platform-side registration. It is **declared in the project's own `services.yaml`** at
that repository's root, same schema as this one. The project's fleet runs under **its own
process-compose instance** on its own fleet API port, generated by the same
`tools/gen_fleet.py` from that registry. And the modules **render in that project's graph
tenant** exactly as devteam's render in tenant 0 — cards with health, a switch, a contract,
an agent and earned mastery.

The plan writes this as `workspaces/<project>/services/<name>/`, shorthand worth correcting
once: there is no per-project workspace directory today — a worker gets a per-attempt
checkout (`workspaces/task-<id>-a<n>/`) and `deploy.py` keeps a per-project one
(`deployments/<project_id>/`, with `branches/<label>/` for previews). The source lives at
`services/<name>/` *relative to whichever checkout is materialised*, and that checkout is
the generator's root. Everything below says "the project root" and means exactly that.

## What already generalises

### The scaffold and the contract

`templates/service/` is already project-neutral — no port, no name and no path in it, config
from `PORT` / `DB_PATH` / `SERVICE_TOKEN` — and `SERVICE_CONTRACT.md` names nothing about
this repository except the generator's filename. Both apply unchanged, and rule 8, *green
under process-compose on first run*, is already an acceptance gate rather than a
description, which is exactly the sentence the manager needs (below).

### The generator

`generate(root, env)` in `tools/gen_fleet.py` already takes a root; `REPO` is only its
default, and `tests/test_fleet_rails.py` already runs it against a temp directory. Every
output path is root-relative. What is **not** project-relative today, audited:

1. **`_env_file` requires a `core` entry.** `CONDUCTOR_URL` is derived with a bare
   `next(... for n, s in managed.items() if s["kind"] == "core")`, so a project registry —
   which has no conductor — makes `generate()` raise `StopIteration`; verified, not
   inferred. A project's fleet must take the conductor's address from the environment the
   generator runs in (the platform is *its* conductor), not from its own registry.
2. **`_port_of` honours `PORT` only for `kind: core`.** A project's ports cannot come from
   literals in a registry an agent wrote, or two projects collide on the first duplicate.
   `generate()` needs an explicit port map (or a block base) as an argument.
3. **The generated content assumes cwd.** `log_location: data/logs/fleet.log` and each
   process's `command: set -a; . data/env/<name>.env; set +a; exec …` are relative, resolved
   against process-compose's working directory; `run-local.sh` gets away with it by doing
   `cd "$(dirname "$0")"` first. A project's fleet must be launched with cwd = the project
   root, or both become absolute.
4. **The interpreter is inside each `cmd:` string.** `defaults.venv` is parsed, defaulted
   and never read — the real interpreter is the literal `.venv/bin/uvicorn` in every entry,
   so a project's runtime has nowhere to be declared. This is the seam where a Node service
   arrives; see the unsolved list.
5. **`KNOWN_DOORS` is the conductor's door list**, validated at generation time, and the
   four doors mean *this* platform. For a project registry it is empty, or it means the
   project-scoped variants (see the model door, below).
6. **Generated secrets land inside the checkout.** `data/tokens/*.token` (0600) and
   `data/env/*.env` are gitignored *here*; inside a user's repository they are untracked
   files a worker's `git add -A` would commit. Either the scaffold carries the ignore lines,
   or generation writes outside the checkout.

`fleet_api.port` is already data, not a constant — one line per project's registry.

### The fleet client

`conductor/app/fleet.py` reads module globals throughout: `_DATA = Path(config.ROOT) /
"data"`, the `_topo` / `_states_cache` / `_spec_cache` singletons, `api_token()` off
`config.ROOT`. The API surface it speaks — `GET /processes`, `POST /process/start/{name}`,
`PATCH /process/stop/{name}`, `GET /process/logs/{name}/0/{n}`, `X-Pc-Token-Key` — is
per-instance already, so the change is mechanical: bind those globals to a root
(`fleet.for_project(pid)`, caches keyed by root) and a project's fleet is a second instance
of a thing that works. Two behaviours survive for free — a missing fleet API answers `None`
and not `{}`, so a project whose fleet is simply not running reads as "I cannot see the
switches"; and `_SHIM_HEALTH` is empty for a project's services, so the beat is pc readiness
plus the service's own `/health`, which is the right answer when there is no shim to ask.

### The Atlas

The part that is most nearly free. `modgraph`'s store is **already multi-tenant** — plans
carry `project_id` (defaulting to 0), and `active_plan`, `mastery` and the rest take it —
and `seed.py` builds a plan from a registry, a working tree and each service's own opening
docstring, so a project's registry needs no new seed logic. Two things are single-tenant:
`seed.py`'s `ROOT` is process-global (`REPO_ROOT`, defaulting to cwd), so the service can
seed only the repository it runs in and it becomes a per-call root on `POST /seed`; and
`routes/graph.py` hardcodes tenant 0 behind `/api/graph/self`, where a project's graph is
the same payload composer against `active_plan(project_id)` and that project's fleet client,
at `/api/graph/project/{id}`. Everything else the Atlas earned — rooms, doors, verbs, the
panel that shows a contract and never a file path — is tenant-agnostic already.

### The gateway

`routes/svc.py` is path-based (`/svc/{name}/{path:path}`), resolves against
`fleet.services()` and adds the service token conductor-side. A project needs a project
segment, and it should be a **prefix**: `/svc/p{project_id}/{name}/{path}`. The reason is
concrete rather than aesthetic — SERVICE_CONTRACT requires every fetch in a service's `ui/`
to be relative (`../health`), so a leading segment is *invisible* to the service's own page
where a trailing one would not be. To keep the namespaces apart, `load_registry` refuses a
service name matching `^p\d+$`: one line, and `/svc/<name>/` keeps meaning the platform's
fleet forever. The auth gate changes shape but not principle — platform services are
root-only unless `public: true`, a project's service is **the project's owner** unless
`public: true` (`owned_project` where `_root` stands today), and neither is ever anonymous.
That one line is how a module says "this genuinely serves its users", a case the platform's
own fleet never had.

### Ports

The locked ranges are conductor 8787, services 8881–8886, fleet API 8899, sandbox
8500–8599, deployed apps 8600–8799. A project's block must not touch any of them.

Proposal: **projects allocate a 16-port block from 9000 upwards** — `base = 9000 + 16*slot`,
where `base` is the project's own fleet API and `base+1 … base+15` its services. That is 62
blocks below 10000, more projects than one box will run for other reasons.
`netports.reserve_port` does the proving — called over the candidate bases with `skip`
carrying the ones already handed out — and the block is then recorded on the project row (a
new `port_base` column), because the reservation must outlive the socket. Be honest about
what that buys: `reserve_port` proves *one* port free at *one* instant by binding it, so the
durable half of the guarantee is the row — it stops the platform colliding with itself, and
the OS remains the referee against everything else on the box. A service whose port is taken fails to bind,
process-compose reports it red and the card says so: visible failure rather than silent
cross-talk, which is the standard the rest of the fleet holds to.

## What the manager must learn

The manager plans a DAG of tasks and hires people. For a service-shaped project it must
plan a DAG of **services** first, and the tasks hang off them.

**Planning modules as services.** Each module carries a contract sketch before anybody
writes code: what it promises in one sentence, the endpoints it will answer, the data it
owns (which is also the answer to "why is this a separate database"). That sketch is exactly
a `services.yaml` block plus a `SERVICE.md`, so the plan is not a document about the code —
it *is* the registry the fleet boots from. The name is the field it cannot fudge: it becomes
the node key, the process name, the `/svc` segment and the log prefix, everywhere.

**The suite before the agent.** A service's tests are written and committed by a different
task than the one that implements it, and that task comes first. This needs no new machinery
— two tasks with a dependency, which `create_tasks` already expresses — only a **refusal**:
`_create_batch` rejects an implementing task for a service with no suite task ahead of it.
It is a refusal and not a prompt for the reason `merge_pr`'s test gate is one: a suite
written after the implementation describes what the implementation happens to do.

**An agent per service.** The project's team already exists (`db.list_agents`) and the graph
already stores a per-node assignment with mastery counted from closed runs, so a service
card is assigned from the project's own roster exactly as the crew's specialists are
assigned to platform services — continuity on one boundary is what mastery means.

**The acceptance gate.** "Comes up green under process-compose on first run" —
SERVICE_CONTRACT rule 8, verbatim, as the condition for accepting the work. Today the
evidence a manager may not override is `worker.run_verification`, which runs the project's
own detected command (`pytest`, `npm test`, `go test`, …) in the worker process precisely so
the model cannot soften the result. The fleet gate is the same idea one layer out — the
fleet boots, every readiness probe passes, every service's suite is green — and belongs in
the same place: evidence gathered by the platform, checked by `merge_pr` and `accept_task`,
overridable only with the boss's agreement.

**Which tools change, and which are new.** `create_tasks` and `add_tasks` gain a `service`
field per item and the suite-before-implementation refusal; `merge_pr` and `accept_task`
gain the fleet gate beside the verification gate they already enforce; everything else is
unaffected. Two are new: **`plan_services`**, which writes the project's `services.yaml` and
scaffolds each declared service from `templates/service/` in one idempotent call (and is
therefore also what makes the project's graph tenant exist), and **`fleet_status`**, which
lets the manager read its own project's process states — the thing the acceptance gate is
judged on. Both cost something: `tests/test_docs_stay_true.py` fails on any new manager tool
until it is documented in `capabilities.CAPABILITIES` and the handbook, or listed in
`UNDOCUMENTED_TOOLS` with a reason. That gate is deliberate — a manager tool is the closest
thing this platform has to a user-facing feature — and should not be routed around.

## What is genuinely hard, and unsolved

**One venv, one language.** The fleet assumes Python everywhere: every `cmd:` is
`.venv/bin/uvicorn`, `templates/service/` is FastAPI with a vendored `helpers.py`, and
`testpaths = tests services` collects every service's suite with the repo's own pytest.
process-compose is not the blocker — it runs a shell command and does not care — the
*scaffold* and the *contract's mechanics* are. A Node service needs its own runtime and
install step, its own health route, its own token check (six lines in any language), its own
committed `openapi.json` and its own WAL sqlite — and its suite cannot be collected by
pytest at all. `worker.detect_verification` returns **one** command for the whole repository,
so a polyglot project cannot say which command proves which service. The options are a
per-language scaffold set (`templates/service-node/`, each restating the nine rules, with
"green under process-compose" as the only shared truth) or one language per project.
Choosing badly gives a contract that means something different per language, or a platform
that can only build Python.

**A project's services and the model door.** A project's service will want a model, and it
cannot hold the owner's credentials, because that is the invariant the whole decomposition
is judged on. The platform's answer exists:
`POST /internal/complete` plus a short HMAC-signed `settings_ref` naming a principal, minted
by the conductor and resolvable only by the conductor, which is how the lifeworld runs a
society of agents on the owner's account having never held a key. What is missing is
**scope**. A project's ref must name the project as well as the owner, so `usage` can
attribute the spend to the project row and not just to the box; it must be revocable when
the project ends or changes hands; and a *deployed* service would go on calling that door
with no session behind it, spending the owner's subscription forever. The honest default is
that it may not, once the project finishes — and there is nowhere in the schema to say so.

**What "deployed" means.** `deploy.py` is singular in every dimension: one checkout at
`deployments/<project_id>/`, one port from `netports.reserve_port(8600, …)`, one
`_wait_healthy` probe, one `running.json` it re-adopts after a conductor restart, one
`RUNNING` slot keyed by project id. A multi-service project breaks all five. Three shapes,
deliberately not chosen here:

- *(a) the deployment is a fleet.* `deploy` runs `process-compose up` in the project's
  checkout; the pid file becomes a fleet API port and token; Stop is `pc down`; the public
  URL is whichever service the registry marks as the entrypoint. Most faithful, most
  machinery, and every branch preview multiplies the port block.
- *(b) one front door.* Exactly one service declares `entrypoint: true`, takes the 8600–8799
  port and deploys as today; the rest are private dependencies started beside it and never
  proxied. Smallest change, and "deployed" still means one URL.
- *(c) no public port at all.* "Deployed" means the project's fleet is up and everything is
  reached through `/svc/p<id>/<name>/`. Nothing to allocate and the auth is already written
  — but no project ever gets a plain URL to hand somebody, which is what deploy exists for.

Rollout, rollback, the staleness check and the k8s path each need a different answer per
option. That is why this is a note and not a plan.

**The cost model.** N services per project × M projects on one box. Each service is a uvicorn
holding tens of megabytes before it does anything, a sqlite file with its own WAL, and a
readiness probe firing every five seconds; each project's fleet is another process-compose
and another unified log. Ten projects of five modules is fifty processes on a box that today
runs seven, and memory runs out well before ports do. Nothing decides *which* project fleets
may be up right now — the platform's own is simply always up, and that cannot survive M
projects. The honest first rule is that a project's fleet runs only while the project is
being built or explicitly deployed and stops with it; nobody has built the thing that stops
them, and a crew improving the platform while fifty orphaned uvicorns hold its memory would
be paying for a decomposition it cannot use.

## The first slice worth building

One project, two services, no manager and no deployment. In order:

1. Make `tools/gen_fleet.py` genuinely root-relative: an explicit port map and conductor
   URL as arguments (removing the `StopIteration` and the `PORT`-is-core-only assumption),
   and a `--root` flag on the CLI. Change nothing else about it.
2. In a throwaway repository, hand-write a `services.yaml` with two services scaffolded
   from `templates/service/`, ports from a block at 9000.
3. Generate against that root and boot `process-compose -f <root>/process-compose.yaml -p
   9000` with cwd = that root.

**Verification**, all of it offline and on this box:

- Both services answer `/health` green on the **first** boot with no manual fiddling —
  SERVICE_CONTRACT rule 8 applied to a project, which is the whole claim in one assertion.
- `pytest` inside that checkout passes with nothing else running.
- The platform's own fleet is untouched: `data/fleet_topology.json` unchanged, the fleet
  API on 8899 still lists exactly its own processes, `/svc/knowledge/health` still answers.
- A test asserts the project's block is disjoint from 8500–8599, 8600–8799, 8787 and
  8881–8899 — the collision is the failure that would be discovered latest and hurt most.

That proves the load-bearing half of this note: the generator, the contract and the fleet
manager are already project-shaped, and two fleets can live on one box without knowing about
each other. Only then is the second slice worth starting — `seed_fleet_graph` against that
root under a `project_id ≠ 0`, rendered at `/api/graph/project/{id}` — because by then the
Atlas is drawing a registry that already exists. The manager, the model door and deployment
stay untouched until both are green.
